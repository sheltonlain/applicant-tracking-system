uestion 1 - Trace your Django forms. Find one class in your project that inherits from forms.Form and one that inherits from forms.ModelForm. For each form, identify what it does and trace how it is used through the application. Explain the important difference between the two forms in your own words.

The ResumeForm in my project inherits from forms.Form, and it allows a resume file to be uploaded and associated with a candidate. The way this works is the candidate_detail function in candidates/views.py contains an empty ResumeForm for each candidate. If a file is uploaded, the resume_upload function puts it in request.FILES and hands it to the form for validation. form.is_valid() is called and makes sure that the file was actually sent and it follows the web app's requirements of only PDF or DOCX files that are smaller than 5MB. When the check passes, the view uses replace_resume to save the file and replace any old files that previously existed. If the check does not pass, the upload fails and displays a warning message explaining what went wrong. This is a plain form (not tied to a model) because replace_resume() needs the previous file's name to delete it. If it was a ModelForm, the new file would be associated on the candidate during validation, and we would no longer have the old file's name in order to delete it.

The CandidateForm in my project inherits from forms.ModelForm, which is connected to a model and can automatically make changes from the validated form data. This form allows you to create and edit candidates in the web application. When a user submits candidate information in the form, the candidate_create function in candidates/views.py validates the data using is_valid(). If the check passes, form.save() creates the new candidate. Similarly, the candidate_edit function allows you to edit candidate data by passing instance=candidate so the form updates only the selected candidate. If either of these fail, the user sees a warning message on what part of the form needs to be fixed.

The difference between the two are that forms that inherit from forms.Form are not connected to a model and cannot save any changes. We have to decide how this data gets used after it is submitted. However, forms that inherit from forms.ModelForm can save the submitted data to the database directly using form.save().

Question 2 - Trace a many-to-many relationship. Identify a many-to-many or association-table relationship in your ATS. Explain which models are connected and why a single foreign key would not represent the relationship correctly. Identify the association table or model and explain whether Django created it automatically or your project defines it explicitly. If it is an explicit association model, explain what data belongs to the relationship itself.

The many-to-many relationship I have chose is between JobOpening and Skill. One job can have many skills associated with it, and one skill can belong to many jobs. We cannot put the FK on either of these alone as it would only point in one direction. Instead, this project creates the link table as the JobSkill model. Django does not create this automatically -- we defined it explicitly. Each row in JobSkill stores the FK from the job and the skill. No extra data is stored.

Question 3 - Explain one prototype decision. Choose either your application-state prototype or your UI prototype. What specific design question was the prototype built to answer? Describe the alternatives you explored, the decision you made after using the prototype, and where that decision appears in your PRD or completed application.

I chose to build a prototype to decide what the job pipeline page should look like and how staff should move applicants between stages. To do so, the agent generated prototypes/pipeline-view-ui.html. In retrospect, I would have also prototyped the logic for the pipeline page to get a better idea of how we should move applicants between stages. However, the ui prototype did also give some valuable insight.

For the UI, there were 3 options: a seperate board for each job with buttons that let you move each card between stages; a similar page that let you drag each card between stages; and a giant table with every application from all jobs.

I chose to use the first option that had buttons to move applications between stages. This felt like the smoothest way to transition the applications to me. I liked the idea of a drag and drop, but since my application only allows applications to advance in order through the pipeline without skipping a hiring step, the drag and drop felt awkward. You could not just simply drop the card wherever you want to, even though it felt like you should be able to. The form of this page that had buttons for advancement mitigated this issue and made the user aware that candidates can only advance one stage at a time. 

This decision is found in the PRD's "pipeline board (one per job)" section (starting at line 190). Our app displays the UI through the board template (applications/templates/applications/board.html), which is written in HTML and Django template language to make the job pipeline appear correctly. 

Question 4 - Defend one code-design decision. Choose one architecture or code-structure decision from your project where the agent recommended one or more options. Explain the options, the decision you approved, and why that choice fits your project. Identify where that decision appears in the completed code.

When walking through the grill-me, the agent recommended that we keep all of the code in a single Django app. I did not feel that this was Django best practice, so I opted to have three apps that reflect the codebase's main focus: candidates, jobs, and applications. Each of these apps have their own objectives, and keeping them separate keeps them easy to navigate and makes the codebase easier to understand. It will also allow the codebase for room to grow in the event that the web application gains more requirements and needs to expand. This decision can be seen in the codebase in the app folders for candidates, jobs, and applications, which contain the models, views, templates, tests, and forms for the respective apps.
